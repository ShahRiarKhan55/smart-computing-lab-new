# 12. Failure-scenario handbook ("what if?")

Legend: **Implemented** = exists in code; **Recommended** = not implemented. "Graceful" is judged from code and tests, not from production incidents.

| # | Scenario | What happens now | Graceful? | What users see | Data at risk | Recovery today | Recommendation |
|---|---|---|---|---|---|---|---|
| 1 | Large number of visitors | Static SPA is served by Vercel's edge; API calls hit one serverless function that scales out per request (platform behavior, DOCUMENTED ONLY). Each API request costs 2 or more database round trips (session lookup, user lookup, then the query). Turso and Vercel plan limits are Unknown | Probably, up to plan limits | slower responses, then 5xx or 429 from the platform | none | wait or raise plan | load test; cache public reads; paginate lists (doc 13) |
| 2 | Database unavailable | Every API call that touches the database fails: session lookup throws, error handler returns a generic 500 (`app.ts:81`). Known contention is a 503 with retry text. Static pages and the shell still load | Partly (no crash loop, clear generic error) | error banners with a retry button (`ErrorState`) | none lost; in-flight writes fail | database provider restores; app recovers on next request | health check that tests the DB; status message page; alert |
| 3 | Hosting platform outage | Site unreachable; no failover region or second host | No | browser error | none | wait for Vercel; redeploy elsewhere is possible but undocumented | document a migration path (doc 17); optional static fallback |
| 4 | User loses connection | `fetch` fails; `useApiResource` shows "Something went wrong" with retry; forms keep input in local state; no offline queue | Partly | error message | unsaved edits only if the page is closed | retry | friendlier offline message |
| 5 | API request times out | No client or server timeout is configured (F-23): the spinner continues until the browser or the platform gives up (platform function limit applies) | No | stuck loading | none | reload | add `AbortController` timeouts and retries |
| 6 | Google OAuth unavailable | Google routes fail closed with short error codes; the login page offers password login; Google only works for already linked accounts | Yes | "Google sign-in is unavailable" style message | none | use password | none needed |
| 7 | User forgets password | **No self-service reset**; an administrator deletes the account and sends a new invitation (their team profile is kept) | Manual | contact the admin | content authored stays (owner becomes null) | admin workflow | email-based reset, or admin-triggered reset link |
| 8 | User tries another user's private data | Messages: 404 unless participant; profile edit by a non-owner: 403; private files: 404; lab-only records: hidden from guests. **VERIFIED** in guards | Yes | "Not found" or "Forbidden" | none | n/a | none |
| 9 | Member opens the admin dashboard | UI redirects to home silently; API answers 403 for admin routes | Yes (UI could explain) | home page | none | n/a | show a "not allowed" message |
| 10 | Admin account compromised | The attacker can change roles, delete accounts and content, publish alumni, read the audit log. No MFA, no session revocation by user (F-02, F-06). Audit rows record actions (field names, not old values) | No | changed or missing content | everything the admin can reach | restore from backup, rotate password, delete sessions manually in the database | MFA, session revocation, break-glass procedure, backups |
| 11 | Malicious file uploaded | Rejected unless its bytes match JPEG, PNG, WebP, GIF or PDF; stored under a random key; images inline with `nosniff`, PDFs as downloads. No malware scan; gallery images keep metadata | Mostly | validation error | a malicious PDF could reach whoever opens it | delete file (owner or manager) | virus scan, restrict PDFs, strip metadata everywhere |
| 12 | Malicious HTML or JavaScript submitted | Stored as text and escaped by React; links must be `http(s)`; the page CSP allows only same-origin scripts. Only build-time Help HTML is injected | Yes | text shown literally | none | n/a | keep avoiding rich text, or add a sanitiser if ever added |
| 13 | Thousands of requests | Login and invitation/Google endpoints are throttled per instance; other endpoints are not (F-14); platform-level protection (Vercel) is Unknown; lists are unpaginated | Partly | slowdowns, platform 429 | none | wait | WAF or rate limits, caching |
| 14 | Two admins edit one record | Edits send only changed fields; last write wins on the same field with no warning (F-15). Duplicate creation is serialised by a write lock; alumni publication uses compare-and-set | Partly | one change silently overwritten | the earlier edit | audit log shows who/when, not old text; restore from backup | version check (`updatedAt`) on update |
| 15 | Migration introduces an error | Executor inspects first, applies only pinned additive statements, verifies after, refuses partial states, requires a recovery point | Yes by design | site pages that read the changed table may 500 if code and schema disagree | the database state | point-in-time restore or manual repair (`turso-migration-executor.md`) | rehearse on a copy (done for publication metadata) |
| 16 | Deployment breaks the site | Previous deployment can be re-promoted in Vercel (platform capability); older code works with additive schema | Yes (manual) | errors until rolled back | none | roll back | smoke-test automation, staged rollout |
| 17 | Database backup is corrupted | Unknown: no repository tooling creates or verifies backups | **Unknown** | n/a | potentially everything | none documented | scheduled export plus restore drill; checksum verification |
| 18 | Uploaded image deleted from storage | `GET /api/files/:id` finds the row but the stream errors, answers 404; the image appears broken; the database row remains | Partly | broken image | the file | re-upload; `storage:reconcile` reports mismatch | store checksums; backup blobs |
| 19 | User deleted while related records exist | Profile unlinked, authored content kept with null owner, reactions/notifications/memberships removed, messages kept with null sender, audit rows keep email snapshots; sessions behave as guest | Yes | content remains | personal data in audit log persists (F-19) | n/a | documented erasure procedure |
| 20 | Hundreds or thousands of users | See doc 13: design is lab-scale; the in-memory limiter, unpaginated lists, per-request double lookups and SQLite semantics become pressure points | Not proven | slower pages | none | scale plan | roadmap in doc 13 |
| 21 | Move to another host | Express app and Prisma work anywhere with Node; replace `api/index.ts` with a long-running `index.ts`, provide a database (SQLite file or Turso), storage (disk or other S3-like; Blob code is isolated in `lib/storage.ts`), env vars, a proxy that sets `X-Forwarded-Proto` (documented trap in `session.ts`) | Feasible, undocumented as a checklist | n/a | n/a | n/a | write a migration runbook |
| 22 | Lab loses an external service | **Vercel:** see 3. **Turso:** database offline (2). **Blob:** uploads fail with 503, existing images break (18). **Google:** only Google sign-in lost (6). **GitHub:** cannot merge; production keeps running. **Google Calendar or Fonts:** schedule iframe or fonts missing; site works | Mostly | degraded features | depends | per service | document an exit plan for each |
